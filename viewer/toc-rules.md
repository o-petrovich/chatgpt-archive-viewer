# Правила формування `topics.json`

Цей розділ є інструкцією для ChatGPT при створенні семантичного змісту з `toc_source.md`.

## Workflow

1. Спочатку повністю прочитати `toc_source.md`.
2. Спочатку сформувати **людський читабельний зміст** без JSON.
3. Користувач переглядає зміст і за потреби коригує його: об'єднує, розділяє, перейменовує, додає пропущені або прибирає зайві теми.
4. Тільки після явного підтвердження користувача створювати `topics.json`.
5. Перед видачею `topics.json` **обов'язково перевірити кожен `start_message_id` і `end_message_id` за цим `toc_source.md`**.
6. Не вигадувати UUID і не відновлювати їх по пам'яті.
7. Якщо точний `end_message_id` визначити надійно не можна, краще поставити останній реально перевірений `message_id` теми або `null`, якщо Viewer це підтримує.

## Формат `topics.json`

```json
{
  "title": "PERF-05 — Gaussian Blur",
  "start_message_id": "abc123",
  "end_message_id": "def456",
  "summary": "Дослідження впливу Gaussian Blur 9×9 на шум, FPS і стабільність детекції.",
  "level": 1
}
```

### Поля

- `title` — коротка читабельна назва пункту у вкладці **Зміст**.
- `start_message_id` — реальний `message_id` повідомлення, з якого логічно починається тема.
- `end_message_id` — реальний `message_id` останнього повідомлення цієї теми.
- `summary` — коротко, що саме обговорювали, досліджували, вирішили або зафіксували у цьому фрагменті.
- `level` — рівень вкладеності: `1` — основна тема, `2` — підтема, `3` — глибший рівень за потреби.

## Правила вибору меж теми

- Межі визначати **семантично**, а не просто за однаковими словами.
- `start_message_id` має вказувати на перше повідомлення, де реально починається нова тема.
- `end_message_id` має вказувати на останнє повідомлення перед переходом до наступної теми.
- Якщо тема починається із повідомлення користувача, бажано ставити саме його `message_id`.
- Якщо суттєва тема починається з відповіді ChatGPT без окремого нового user-повідомлення, допустимо ставити `message_id` ChatGPT.
- Не використовувати службові tool/reasoning повідомлення як тематичні anchors.
- Не використовувати `message_id` із цитованих старих файлів, GitHub, filecite або вкладених фрагментів — тільки `message_id`, що явно присутні у поточному `toc_source.md`.

## Якість змісту

Зміст має описувати **реальні етапи розмови**, а не бути простим переліком ключових слів.

Добрий пункт:
- охоплює логічно завершений блок;
- має зрозумілу назву;
- не дублює сусідній пункт;
- не дробить один експеримент на безліч дрібних записів без потреби;
- не ховає важливу окрему тему всередині занадто широкого пункту.

Для довгих технічних чатів зазвичай краще 8–15 змістовних тем, ніж десятки дрібних пунктів.

## Обов'язкова перевірка перед видачею JSON

Перед створенням фінального файла:

1. Зібрати всі `message_id:` із `toc_source.md`.
2. Для кожної теми перевірити, що `start_message_id` і `end_message_id` існують, а початок іде раніше за кінець.
3. Не покладатися на попередньо згенерований JSON без повторної перевірки.
4. Якщо Viewer відхиляє ID — повернутися до `toc_source.md` і виправити **всі** ID, а не тільки перший помилковий.

## Важливо

`toc_source.md` є джерелом істини для тематичних anchors. `conversation.json` залишається незмінним. `topics.json` можна повторно генерувати, редагувати й замінювати без зміни самого архіву чату.
